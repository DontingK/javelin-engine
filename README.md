# Javelin Engine

> [中文说明](README.zh-CN.md)

**A PC-focused 3D game engine with a built-in Unity-style editor — written in Java, rendered on Vulkan, shipped as a native executable.**

Javelin gives you the workflow you know from Unity (Hierarchy, Inspector, drag-and-drop assets, one-click build) in modern Java, on a Vulkan renderer, with games deploying through GraalVM native-image. It deliberately targets **desktop PC only**: no mobile constraints, no lowest-common-denominator rendering, no features cut for weak hardware. It is early stage (`0.1.0`, Windows-first), but the full loop already runs end-to-end: create a project, build a scene, save and reload, then package a playable build — as JAR or as a native `.exe`.

## Why Javelin

### A complete editor, not just an SDK

Most Java engines hand you a `main()` and a wiki. Javelin ships a real desktop editor (Swing + FlatLaf): docked **Hierarchy / Project / Inspector** panels, a transform gizmo you can drag, **GPU ID-buffer picking**, a Unity-style scene-view fly camera, world-space debug lines, and a full menu & command system. Editing a component means editing its fields — the inspector is driven by reflection annotations, and the UI ships in English and 简体中文.

### Vulkan, not OpenGL

The rendering backend is a Vulkan RHI built on LWJGL 3: render graph, multi-camera with per-camera viewport / clear flags / depth ordering, a forward pipeline with transparent sorting, MSAA, and FIFO / MAILBOX present modes. Debug overlays are built in — render stats and on-screen debug text toggle with `F3`.

### AOT: Java games ship as native executables

Distribution is where Java games usually die — JRE bundles, hundreds of megabytes, fragile classpaths. Javelin makes it one click: the editor packages your game either as a self-contained folder (`game.jar` + jlink-trimmed runtime) or as a **native executable via GraalVM native-image**, with LWJGL DLLs placed beside the exe. The engine was built for AOT from day one — explicit reflective registration replaces classpath scanning, and `reflect-config.json` is generated by an annotation processor at compile time — so a game behaves identically on the JVM and as a native image.

### Unity-style asset & material workflow

GUIDs with companion `.meta` files, drop-in import with focus-scan auto refresh (Unity *Auto Refresh*), and ShaderLab-inspired `.shader` files compiled to SPIR-V at import. Materials carry UBO parameters, texture slots and multi-material sub-meshes; built-in primitives (plane / cube / sphere / capsule / cylinder) come ready to place. A broken shader falls back to a default material instead of crashing the frame loop, and shader hot-reload is wired into the editor.

## Also included

- **Scene model** — Node / Component / Transform with life-cycle frame driving, `.scene` text serialization
- **Physics queries** — ray / sphere / box / cylinder / AABB math, scene-level `Physics.raycast` / `raycastAll` with layer masks
- **Input** — keyboard / mouse with bindable actions and edge-detection frame semantics
- **Textures** — layered asset model: one image, many texture settings, no file duplication
- **Plugins** — discovered via `ServiceLoader`; the editor core itself is just a plugin

## Tech stack

| Area | Technology |
|------|------------|
| Language | Java 25 |
| Rendering | Vulkan via LWJGL 3 (Vulkan / GLFW / shaderc bindings) |
| Editor UI | Swing + FlatLaf, JSVG for icons |
| Math | JOML |
| Codegen | javac annotation processing — compile-time reflective registration |
| Build & packaging | Gradle 9.2, jlink, GraalVM native-image |
| Logging | slf4j + logback |
| Tests | JUnit |

## Requirements

- **GraalVM for JDK 25** — any JDK 25 build works for JVM-side development and JAR packaging (jlink ships with the JDK); native-image AOT builds require GraalVM, plus MSVC / Visual Studio Build Tools on Windows
- **Windows 10+** with a Vulkan-capable GPU/driver (Linux untested; macOS unsupported for now — no MoltenVK)
- Gradle 9.2 (wrapper included)

## Getting started

```bash
# build everything and run the test suite
./gradlew build

# publish engine artifacts to mavenLocal (needed by editor-created game projects)
./gradlew publishToMavenLocal

# run a rendered demo (replace the class with any test under javelin-core/src/test)
./gradlew :javelin-core:runTest -DmainClass=cn.donting.javelin.core.MultiCameraDemo
```

The editor itself has no Gradle run task yet — launch the main class `cn.donting.javelin.editor.JavelinEditor` from your IDE.

## Use the engine from another project

Editor-created game projects are standard Gradle builds that consume the engine from `mavenLocal`:

```groovy
dependencies {
    implementation 'cn.donting.javelin:javelin-core:0.1.0-SNAPSHOT'
}
```

## Modules

| Module | Description |
|--------|-------------|
| `javelin-rhi` | Vulkan rendering backend (RHI): device / swapchain / render graph / PSO cache / SPIR-V loading |
| `javelin-core` | Engine core: scene, rendering systems, materials, assets, input, physics queries, debug overlays |
| `javelin-ast` | Annotation processor that generates explicit reflective registration (no runtime classpath scanning) |
| `javelin-log` | Logging module (slf4j + logback) |
| `javelin-tool` | Offline asset-generation CLIs (shaderc compilation, debug-text font rasterizer) |
| `javelin-editor` | The Swing editor application |
| `project-template` | Gradle template copied when the editor creates a new game project |

## Documentation & roadmap

Detailed design documents (Chinese, incl. decision records and pitfalls) live under [`doc/`](doc/); feature/acceptance status is tracked in [`Engine_Features.md`](Engine_Features.md), the phase roadmap in [`doc/Engine_Roadmap.md`](doc/Engine_Roadmap.md).
